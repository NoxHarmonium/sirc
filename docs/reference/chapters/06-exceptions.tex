\chapter{Exception and Interrupt Handling}
\label{ch:exceptions}

\section{Overview}

An exception is an event that causes the program flow to be diverted to an address stored in a predefined vector.

Some are directly caused by an instruction, some are a side effect of an instruction, and some are asynchronously
caused by external hardware.

They are managed by the exception coprocessor, which takes control of the processor when an exception is pending.
Figure~\ref{fig:exception-coprocessor} shows how the pieces fit together; each is described in the sections that
follow.

\subsection{Exception Levels and Priority}
\label{sec:exception-levels-and-priority}

Exceptions are prioritized as follows (highest to lowest):

\begin{enumerate}
	\item Priority 7: Faults
	\item Priority 6: Level 5 (L5) hardware exceptions (NMI-like)
	\item Priority 5: Level 4 hardware exceptions
	\item Priority 4: Level 3 hardware exceptions
	\item Priority 3: Level 2 hardware exceptions
	\item Priority 2: Level 1 hardware exceptions
	\item Priority 1: Software exceptions (traps)
\end{enumerate}

Faults have priority over all hardware interrupts. If a fault is pending at the same instruction boundary as one or
more hardware interrupts, the fault is dispatched first and the hardware interrupts remain pending. This includes
instruction trace faults: when trace mode raises a post-instruction fault, that trace fault is serviced before pending
hardware interrupts at the next boundary.

\textbf{Hierarchical Exception Handling:}

Exceptions in SIRC-1 are strictly hierarchical. A hardware interrupt can only interrupt the current execution if its
priority level (exception level) is \textit{higher} than the currently active exception level. This prevents:

\begin{itemize}
	\item An interrupt handler from being interrupted by its own interrupt (same level)
	\item Lower priority interrupts from interrupting higher priority handlers
\end{itemize}

Software exceptions follow a separate rule. An \mnemonic{EXCP} executed inside any exception or fault handler is
discarded rather than deferred, so a trap can never overwrite link register 0 (Section~\ref{sec:user-exceptions}).

The exception unit maintains a \texttt{current\_exception\_level} field that tracks the active exception level (0--7).
When not handling any exception, this is 0. When handling an exception at level N, only exceptions at level > N can
interrupt. Two cases fall outside this rule. Faults are dispatched at any level: a fault raised inside a fault handler
becomes a double fault. A Level 5 request that arrives while a Level 5 handler is running (level 6) is not deferred but
raises a Level Five Hardware Exception Conflict fault (Section~\ref{sec:level-five-conflict-fault}).

\subsection{Vector Table}

The exception vectors are stored starting at address \addr{0x0}. Each vector is a 24-bit target address stored as two
consecutive 16-bit words in the address format described in Section~\ref{sec:exception-vector-storage}. The high word
is stored first at \texttt{vector * 2}, followed by the low word at \texttt{vector * 2 + 1}. The vector table has 256
entries. Vectors \texttt{0x00}--\texttt{0x5F} (96 entries) are reserved for the CPU; vectors
\texttt{0x60}--\texttt{0xFF} (160 entries) are user trap vectors. Supervisor code can still name a CPU vector in
\mnemonic{EXCP}; it is entered as an ordinary trap (see \mnemonic{EXCP} in Chapter~\ref{ch:coprocessor}). The vector
table layout is:

\begin{itemize}
	\item \textbf{\texttt{0x00}:} Reset vector
	\item \textbf{\texttt{0x01}:} Bus fault
	\item \textbf{\texttt{0x02}:} Alignment fault
	\item \textbf{\texttt{0x03}:} Segment overflow fault
	\item \textbf{\texttt{0x04}:} Invalid opcode fault
	\item \textbf{\texttt{0x05}:} Privilege violation fault
	\item \textbf{\texttt{0x06}:} Instruction trace fault
	\item \textbf{\texttt{0x07}:} Level five hardware exception conflict
	\item \textbf{\texttt{0x08}:} Double fault
	\item \textbf{\texttt{0x09}:} Bus protection fault
	\item \textbf{\texttt{0x0A}--\texttt{0x0F}:} Reserved for future privileged exceptions
	\item \textbf{\texttt{0x10}:} Level 5 hardware exception vector
	\item \textbf{\texttt{0x20}:} Level 4 hardware exception vector
	\item \textbf{\texttt{0x30}:} Level 3 hardware exception vector
	\item \textbf{\texttt{0x40}:} Level 2 hardware exception vector
	\item \textbf{\texttt{0x50}:} Level 1 hardware exception vector
	\item \textbf{\texttt{0x11}--\texttt{0x5F} (excluding \texttt{0x20}, \texttt{0x30}, \texttt{0x40}, \texttt{0x50}):} Reserved
	\item \textbf{\texttt{0x60}--\texttt{0xFF}:} User exception vectors (160 user-accessible trap vectors)
\end{itemize}

\subsection{Instructions Used in This Chapter}

This chapter refers to several exception-coprocessor instructions before their full reference entries appear. Briefly:

\begin{description}
	\item[\mnemonic{EXCP}] Triggers a software exception (trap).
	\item[\mnemonic{RETE}] Returns from an exception handler, restoring the saved program counter, status register, and
	      exception level.
	\item[\mnemonic{WAIT}] Stops instruction fetch until an interrupt that can be taken, or a reset, occurs.
	\item[\mnemonic{RSET}] Performs the reset sequence and jumps to the reset vector.
	\item[\mnemonic{ETFR}] Copies the saved return address and/or status register from a link register into \reg{a}
	      and/or \reg{r7}.
	\item[\mnemonic{ETTR}] Copies \reg{a} and/or \reg{r7} into a link register's saved return address and/or status
	      register.
\end{description}

\mnemonic{EXCP}, \mnemonic{RETE}, \mnemonic{WAIT}, \mnemonic{RSET}, \mnemonic{ETFR}, and \mnemonic{ETTR} are
meta-instructions that assemble to \mnemonic{COPI} (coprocessor call) forms addressed to the exception coprocessor
(coprocessor \texttt{0x1}); Section~\ref{sec:exception-coprocessor-instructions} in this chapter lists
their opcodes, and Chapter~\ref{ch:coprocessor} gives the full syntax, operation, flags, and legal forms for each.

\section{Faults}

Faults are priority 7 exceptions raised by the CPU itself in response to error conditions or debug events. They use
vectors in the \texttt{0x01}--\texttt{0x0F} range. Unlike hardware and software exceptions, faults cannot be masked or
deferred: once a fault condition is raised, the fault is dispatched at the next instruction boundary regardless of the
current exception level. Two faults are conditional on whether they are raised at all: Segment Overflow requires
\texttt{SR.A}, and Instruction Trace requires \texttt{SR.T} or the force-trace request (\texttt{TRCE}).

\subsection{Fault Categories}
\label{sec:fault-categories}

Not all faults behave the same way with respect to the faulting instruction and the \mnemonic{RETE} return address.
There are three categories:

\subsubsection{Retryable faults}
The operation that triggered the fault does not take effect. For most faults this means the instruction takes no
architectural effect (the exceptions to this are listed below). The link register stores the address of the faulting
instruction. \mnemonic{RETE} returns to that instruction so it can be retried, typically after the fault handler has
corrected the condition that caused the fault.

Examples of how a handler can correct the cause of a fault:

\begin{itemize}
	\item Remapping or paging in a device for a bus fault
	\item Switching to supervisor mode for a bus protection fault or privilege violation
	\item Bringing an out-of-range address back into range for a segment overflow
	\item Emulating the missing operation for an invalid opcode fault
\end{itemize}

Every fault in this category follows the same pattern: a handler is always free to advance past the faulting
instruction with \mnemonic{ETFR}/\mnemonic{ETTR} instead of retrying it. For Invalid Opcode Fault this is usually the
right choice -- simply retrying an unemulated invalid opcode will raise the same fault again.

Two cases do not follow the pattern of the instruction being cancelled before it commits:

\begin{itemize}
	\item An alignment fault is raised at phase 0, before the instruction fetch reaches the bus, so there is no decoded
	      instruction to cancel.
	\item A DMA burst (\mnemonic{DMAR}, \mnemonic{DMAW}, \mnemonic{DMAT}) performs several bus accesses per instruction; a fault
	      partway through can leave some of those accesses already committed; see the individual fault descriptions below and
	      Section~\ref{sec:dma-fault-retry}.
\end{itemize}

The retryable faults are: \textit{Alignment Fault; Bus Fault; Bus Protection Fault; Invalid Opcode Fault; Privilege
	Violation Fault; Segment Overflow Fault.}

\subsubsection{Post-instruction faults}
The instruction completes normally and its effects are committed before the fault fires. The link register stores the
address of the \textit{next} instruction. \mnemonic{RETE} advances to that instruction; the traced instruction is not
re-executed.

The only post-instruction fault is the \textit{Instruction Trace Fault}.

\subsubsection{Exception dispatch faults}
Raised during the exception handling machinery itself, not during normal instruction execution. The link register
stores the program counter at the point the fault was detected within the exception handler. The one exception is a
double fault caused by a failed fault-vector fetch, which keeps the original fault's return address
(Section~\ref{sec:double-fault-vector-fetch}). For a double fault raised inside a fault handler by a retryable fault,
the point the fault was detected is the instruction that raised it, so the link register stores that instruction's
address, as the escalating fault would have done on its own. Recovery may require careful state management; these
faults often indicate a hardware misconfiguration or a programming error in an exception handler.

The exception dispatch faults are: \textit{Level Five Hardware Exception Conflict, Double Fault.}

\subsection{Bus Fault}

\textit{(Retryable)} -- Raised when the external memory system reports a bus transaction as failed by signaling a bus error
(\texttt{BERR}).

This could happen, for example, if an unmapped address is presented by the CPU and another device detects this and
raises an error. The instruction is cancelled before it takes effect, and the link register stores the address of the
\textit{faulting} instruction, so a handler implementing virtual memory can map in the missing page and return with
\mnemonic{RETE} to retry the same instruction.

Because ALU results and status-register updates are only committed during the write-back phase
(Chapter~\ref{ch:cpu-architecture}), which runs after the memory-access phase where a bus fault is detected but does
nothing for a cancelled instruction, a bus fault can never leave a partial status-register or register update behind
for an ordinary single-access instruction.

This atomicity does not extend to a DMA burst: \mnemonic{DMAR}, \mnemonic{DMAW}, and \mnemonic{DMAT} are each one
instruction that performs multiple bus accesses in sequence, so a bus fault partway through a burst leaves the words
already transferred in effect -- retrying with \mnemonic{RETE} does not undo them. The fault metadata register's DMA
read/write burst bus-access-type codes (Section~\ref{sec:fault-metadata-register-format}) let a handler recognize this
case. See Section~\ref{sec:dma-fault-retry} for what a handler can safely do about it.

\subsection{Bus Protection Fault}

\textit{(Retryable)} -- Raised when the external memory system reports a bus protection error (\texttt{BPER}) in response to a bus
transaction.

This indicates that the requested address and device are valid, but the operation is disallowed. Examples include
writing to ROM or accessing a protected memory region while the CPU is in protected mode. The instruction is cancelled
before it takes effect, and the link register stores the address of the faulting instruction, so a handler can make the
necessary corrections and retry with \mnemonic{RETE}.

As with Bus Fault, this applies cleanly to an ordinary single-access instruction; a DMA burst (\mnemonic{DMAR},
\mnemonic{DMAW}, \mnemonic{DMAT}) can raise this fault partway through, in which case words already transferred before
the fault remain in effect. See Section~\ref{sec:dma-fault-retry} for what a handler can safely do about it.

\subsection{Alignment Fault}

\textit{(Retryable)} -- Raised when fetching instructions if the program counter
contains an odd word address. The check is made at phase 0, before the fetch's bus cycle, so the odd address never
reaches the bus. No instruction slot is used: the fault's dispatch slot begins at that same phase 0. The fault-metadata
register records bus access type \texttt{0x1} (instruction fetch) and the odd address that would have been fetched.

This is to simplify fetching: the second word of an instruction is always at \texttt{pl | 0x1}, which ensures that
instructions can never overflow a segment boundary. The saved return address is itself odd; a fault handler must
correct the saved return address in link register 6 (for example, by clearing bit 0 using \mnemonic{ETFR} and
\mnemonic{ETTR}) before returning with \mnemonic{RETE}, or the CPU raises the same fault again immediately.

\subsection{Segment Overflow Fault}
\label{sec:segment-overflow-fault}

\textit{(Retryable)} -- Raised when a computed address would fall outside the
current segment.

Only raised if \texttt{SR.A} (Trap on Address Overflow) is set, since some programs intentionally rely on address
wrap-around. With \texttt{SR.A} set, there are two cases:

\begin{itemize}
	\item An effective-address calculation wraps the low address word. The instruction is cancelled before it takes effect, and
	      the link register stores its address, so a handler can bring the address back into range and retry with
	      \mnemonic{RETE}. The fault metadata register records the wrapped address and the bus access it was computed for:
	      \texttt{0x2} (data read) or \texttt{0x3} (data write) for \mnemonic{LOAD} and \mnemonic{STOR}, \texttt{0x1}
	      (instruction fetch) for the target of a branch, \mnemonic{LDEL}, \mnemonic{BRSR}, or \mnemonic{LJSR}, and \texttt{0x0}
	      (none) for \mnemonic{LDEA}, which makes no access with it. No bus cycle is performed in any of these cases.
	\item The instruction in the last slot of the segment would wrap the program counter's low word as it advances. The AU checks
	      this in phase 3, before any memory access, for every instruction that uses the advanced address: as the next program
	      counter (any instruction that does not branch, including a coprocessor call, and a branch whose condition is false), or
	      as the return address saved in \reg{l} (\mnemonic{LDEL}, \mnemonic{BRSR}, \mnemonic{LJSR}). A taken branch or jump that
	      writes \reg{p} without saving a return address does not use it and does not fault, and neither does an ALU or
	      \mnemonic{LOAD} instruction that writes \reg{pl} (Section~\ref{sec:address-registers}). The instruction is cancelled
	      and the link register stores its own address, as for any other retryable fault. No bus access is involved, so the fault
	      metadata register records bus access type \texttt{0x0} (none). Retrying with \mnemonic{RETE} raises the same fault
	      again, so a handler must emulate the instruction or redirect the saved return address with
	      \mnemonic{ETFR}/\mnemonic{ETTR}. With \texttt{SR.A} set, the last instruction slot of a segment can therefore only
	      usefully hold a taken branch or jump.
\end{itemize}

The same DMA-burst caveat as Bus Fault and Bus Protection Fault applies here: a segment-overflow fault raised partway
through a \mnemonic{DMAR}, \mnemonic{DMAW}, or \mnemonic{DMAT} burst does not undo words already transferred before the
fault. See Section~\ref{sec:dma-segment-overflow} for where a DMA burst checks for overflow and
Section~\ref{sec:dma-fault-retry} for what a handler can safely do about it.

\subsection{Invalid Opcode Fault}

\textit{(Retryable)} -- Raised when a coprocessor call targets a coprocessor
ID not implemented by the selected CPU model, or an operation that the coprocessor it targets does not implement.

Can be used for forward compatibility: programs written for a future coprocessor (for example, a floating-point unit)
will trap on older hardware, and the handler can emulate the operation in software. Because this fault is retryable,
the link register stores the address of the faulting instruction; a handler that has emulated the operation must use
\mnemonic{ETFR}/\mnemonic{ETTR} to redirect the return address to the instruction following the trapped call before
returning with \mnemonic{RETE} -- retrying the instruction unmodified will simply raise the same fault again.

Note that this fault is specific to coprocessor instructions. Other instruction encodings outside the documented
instruction set are reserved or architecturally undefined, and do not raise an invalid-opcode fault.

\subsection{Privilege Violation Fault}

\textit{(Retryable)} -- Raised when a privileged operation is attempted
while not in supervisor mode:
\begin{enumerate}
	\item Directly writing to the high word of any address register
	\item Address-register-pair write-back that would change a high address-register word
	\item Executing a supervisor-only coprocessor operation
	\item Triggering a software exception with a vector below \texttt{0x60}
\end{enumerate}

Figure~\ref{fig:privilege-checks} (Chapter~\ref{ch:registers}) shows where each of these checks is made.

The illegal instruction never takes effect: it is cancelled before it writes anything, and the link register stores its
own address so \mnemonic{RETE} returns to it directly. This matters because a supervisor-mode handler needs to be able
to inspect the exact instruction that faulted, decide how to respond (deny it, emulate its effect, or promote the
caller), and then either retry it or use \mnemonic{ETFR}/\mnemonic{ETTR} to redirect the return address elsewhere. None
of that is possible if the illegal instruction had already been allowed to run.

\subsection{Instruction Trace Fault}
\label{sec:instruction-trace-fault}

\textit{(Post-instruction)} -- Raised after every instruction completes
when \texttt{SR.T} is set, or when the force-trace request (\texttt{TRCE}) is active at the instruction boundary
(see the Force Trace Mode Input in the \textit{SIRC-1 Hardware Reference Manual}).

Used for single-step debugging. The fault fires after the instruction commits; for a coprocessor call, that includes
the call's dispatch slot (Section~\ref{sec:interrupt-latency}). \mnemonic{RETE} returns to the instruction
\textit{following} the traced one. The T bit is cleared on entry to the fault handler (as with all exceptions), so the
handler itself is not traced. \mnemonic{RETE} restores the saved SR, which re-enables tracing unless the handler
explicitly clears T from the saved status register via \mnemonic{ETTR} before returning. \texttt{SR.T} is sampled once
at the start of each instruction, before that instruction can modify it, so a write to \texttt{SR.T} takes effect
starting with the next instruction boundary; exception-unit dispatches are never traced.

A traced \mnemonic{EXCP} is the one exception to the rule that a call's command completes before its trace fault. The
trace fault is taken first, with the link register storing the address after the \mnemonic{EXCP}, and the exception
unit records the trap as a pending software exception instead of entering it. When the trace handler returns with
\mnemonic{RETE} to exception level 0, the recorded trap is entered at that instruction boundary as if the
\mnemonic{EXCP} had just executed: link register 0 stores the address after the \mnemonic{EXCP} and the status register
restored by the trace handler. A debugger single-stepping through a system call therefore stops once before the trap
handler runs, and again at the instruction after the \mnemonic{EXCP} once the handler has returned.

Trace faults are not raised while a fault handler runs (exception level 7), whether \texttt{SR.T} is set or
\texttt{TRCE} is active, because each one would otherwise escalate to a double fault. A handler at a lower level is
traced if it sets \texttt{SR.T} itself or if \texttt{TRCE} is active.

\subsection{Level Five Hardware Exception Conflict}
\label{sec:level-five-conflict-fault}

\textit{(Exception dispatch)} -- Raised when a Level 5 hardware exception cannot be handled normally because it
collides with another one. There are two cases:

\begin{itemize}
	\item A Level 5 hardware exception is dispatched while one is already being serviced (exception level 6).
	\item The exception unit is about to dispatch a queued Level 5 hardware exception, but one or more further Level 5 requests
	      arrived while it was queued and could not be queued as well (the \emph{L5 overrun} described in
	      Section~\ref{sec:level-5-nmi-behavior}).
\end{itemize}

In the first case the fault consumes the pending request: it is not dispatched after the handler returns. In the second
case the request stays pending and is dispatched after the fault handler returns. If both cases apply at once, a single
fault is raised, and it also clears the L5 overrun flag.

The exception unit has no spare link register above level 6, and the pending hardware exceptions register holds only
one bit per line, so a second L5 cannot be handled normally. Rather than silently dropping it (which could mask a
hardware misconfiguration), the CPU raises this fault. Level 5 interrupts should be treated as NMIs.

A program that does not care about conflicting L5 requests can install a handler for this fault that consists of a
single \mnemonic{RETE}; the fault is not retryable, so \mnemonic{RETE} resumes the code that was running when the fault
was raised. A program that does care can use the handler to log the overrun or take corrective action.

\subsection{Double Fault}
\label{sec:double-fault}

\textit{(Exception dispatch)} -- Raised when a fault occurs while another fault is
already being handled, or when a fault's own vector cannot be fetched (Section~\ref{sec:double-fault-vector-fetch}).

When the CPU is already at fault level (priority 7) and another fault occurs, there is no additional banked link
register available. The fault link register (register 6) is overwritten with the new return address, losing the
original fault's return address. The fault metadata register (register 7) is also overwritten; it records the double
fault flag, the original fault's type, and the type of the fault that caused the escalation
(Section~\ref{sec:fault-metadata-register-format}).

The CPU jumps to vector \texttt{0x08}. This is typically a last-chance handler that dumps registers and resets. If
another fault occurs while the CPU is already at fault level, the CPU attempts to dispatch vector \texttt{0x08} again.
There is no limit to the number of times vector \texttt{0x08} is dispatched. A double fault handler that causes a fault
may cause an infinite loop without special handling from the programmer. If the double-fault vector fetch itself fails,
the CPU will reset. An instruction raises at most one fault: the first one detected cancels it, and the checks in its
remaining phases are not made (Section~\ref{sec:exception-and-fault-timing}).

\subsubsection{Link Register Preservation}

There is no way to fully recover from a double fault raised inside a fault handler: the valid response is to declare
the CPU state invalid, perform some last-chance error handling (for example, dumping the registers), and reset the CPU.

A fault handler that wants a better chance of capturing useful diagnostics before that reset should still save the link
register contents early -- before doing anything else that might fault again -- using the \mnemonic{ETFR} instruction,
so the original fault's return address and status register can be included in whatever gets dumped.

The values can be stored on the stack but since the stack pointer may be corrupted, a more robust implementation stores
and loads from hardcoded memory addresses that are known to always be valid, instead of relying on the stack pointer.

\mnemonic{ETFR} only transfers the return address and status register of link registers 6 and 7; the saved exception
level is not accessible to software through it, nor can \mnemonic{ETTR} write it back. This is not just a missing
diagnostic field: \mnemonic{RETE} always restores \texttt{current\_exception\_level} directly from whatever value is
currently latched in the link register, and after a double fault raised inside a fault handler that value is the fault
level (7), not the level that was active before the original fault. Even a handler that perfectly restores the return
address and status register and attempts \mnemonic{RETE} anyway would leave the CPU stuck at exception level 7 -- unable
to service any hardware interrupt or software exception, including Level 5, since nothing outranks the highest priority
level. New faults still dispatch normally regardless of the stuck level (faults bypass the priority check), so the CPU
would keep running rather than visibly failing; it would simply be deaf to every interrupt and trap for the rest of the
program's life. This is the underlying reason reset, not \mnemonic{RETE}, is the only valid response to a double fault
raised inside a fault handler.

\subsubsection{Fault Vector Fetch Failure}
\label{sec:double-fault-vector-fetch}

A double fault is also raised when the vector fetch for a fault fails with a bus or bus protection fault. This case is
different from a fault raised inside a fault handler, because exception entry commits only after the vector fetch
succeeds (Section~\ref{sec:exception-entry-side-effects}). The original fault never entered its handler, so nothing has
been overwritten yet:

\begin{itemize}
	\item The CPU is still at the exception level from before the original fault.
	\item Link register 6 receives the original fault's return address, the status register from before the original fault, and
	      that exception level, exactly as the original fault would have saved them.
	\item The fault metadata register has the double fault flag set and bus access type \texttt{0x4} (exception vector fetch).
	      The Original Fault field holds the fault whose vector could not be fetched, the Escalating Fault field holds the bus or
	      bus protection fault raised by the fetch, and the Return Address field holds the vector-table address that failed.
\end{itemize}

A double fault raised inside a fault handler never records an exception vector fetch, so a double-fault handler can
identify this case from the double fault flag together with bus access type \texttt{0x4}.

Unlike a double fault raised inside a fault handler, this case is recoverable: \mnemonic{RETE} restores the state from
before the original fault and returns to the original fault's return address. The handler must first repair whatever
made the vector fetch fail, typically the vector-table entry or the memory mapping that holds it. For a retryable
original fault, \mnemonic{RETE} retries the faulting instruction, which raises the original fault again; if its vector
still cannot be fetched, the CPU double faults again and loops. If the original fault was an Instruction Trace Fault or
a Level Five Hardware Exception Conflict, \mnemonic{RETE} continues past it and that fault is not raised again.

\section{Hardware Exceptions (Interrupts)}

A hardware exception occurs when external hardware raises an interrupt request. These are also referred to as
``interrupts''. When a hardware exception occurs, the current instruction is completed, and control is transferred to
different vectors based on the interrupt ``priority''. The vectors for hardware exceptions are in the
\texttt{0x10}--\texttt{0x50} range.

The return address stored in the exception link register is the address of the instruction that would have executed
next, not the interrupted one -- so once the handler returns via \mnemonic{RETE}, the interrupted program resumes
normally as if nothing happened.

\subsection{Hardware Interrupt Enable Bits}
\label{sec:hardware-interrupt-enable-bits}

The status register contains 4 individual enable bits (bits 9--12 in the privileged byte) that control whether each
maskable hardware interrupt line can trigger an exception:

\begin{itemize}
	\item Bit 9 (E1): Hardware Interrupt Line 1 (Level 1, lowest maskable priority)
	\item Bit 10 (E2): Hardware Interrupt Line 2 (Level 2)
	\item Bit 11 (E3): Hardware Interrupt Line 3 (Level 3)
	\item Bit 12 (E4): Hardware Interrupt Line 4 (Level 4, highest maskable priority)
\end{itemize}

\textbf{Note:} Hardware Interrupt Line 5 (Level 5) is a Non-Maskable Interrupt (NMI) and cannot be disabled.
It will always trigger an exception when requested, regardless of the enable bit settings. Bit 13 is used for the
Exception Active flag instead.

When an interrupt line is disabled (bit = 0), interrupts on that line are completely ignored and not queued. When
enabled (bit = 1), the interrupt can trigger an exception if its priority is higher than the currently executing
exception level.

\subsection{Pending Hardware Interrupts}
\label{sec:pending-hardware-interrupts}

Interrupt requests at levels 1--4 are level-sensitive; Level 5 is edge-triggered and is described separately in
Section~\ref{sec:level-5-nmi-behavior}. When an enabled level-sensitive interrupt request is observed active, the
corresponding bit is set in the pending hardware-exceptions register. The request lines are sampled on every clock
cycle against the current enable bits. Requests at disabled maskable levels are ignored and are not latched for later
service. A line is also not latched while the current exception level is at or above the level its own handler would
run at, that is, while its own handler or a higher-priority one is running. Without this rule, a request that is still
active when its handler starts would be latched again before the handler could acknowledge the device, and the handler
would be dispatched a second time after \mnemonic{RETE} with no request behind it. A device must therefore hold its
request until it is serviced: a request withdrawn while a handler at or above its level runs is not seen. A write to
\reg{sr} that sets an enable bit therefore lets an already-active request on that line be dispatched at the next
instruction boundary, straight after the instruction that set it. A write that clears an enable bit does not discard a
request already latched on that line; see below.

For the level-sensitive lines, the pending register stores one bit per hardware interrupt line, so repeated requests at
the same level coalesce into a single pending interrupt. If the request is still active after its handler returns with
\mnemonic{RETE}, it is sampled again and becomes pending again.

At an instruction boundary, the exception unit selects the highest-priority pending hardware interrupt whose priority
is higher than the current exception level. The selected bit is cleared as the handler is dispatched, and set again if
the handler's vector fetch fails (Section~\ref{sec:exception-entry-side-effects}). Lower-priority interrupts latched
before the handler was entered remain latched and are considered again after the current handler returns with
\mnemonic{RETE}. If the highest-priority pending interrupt's enable bit has been cleared since it was latched, it does
not block dispatch of any other pending, enabled interrupt of lower priority. The disabled interrupt stays pending, and
is dispatched if its line is re-enabled, even if the device has since withdrawn its request.

\subsection{Interrupt Recognition and Latency}
\label{sec:interrupt-latency}

Hardware interrupts, software exceptions and instruction trace faults are recognized only at an instruction boundary,
and only when the CSR is empty and no coprocessor is active (Section~\ref{sec:coprocessors-and-csr}). A coprocessor
call (\mnemonic{COPI}, \mnemonic{COPR}, or a meta-instruction that assembles to one) is part of its instruction: its
dispatch slot, and the command it starts, complete before a pending hardware interrupt or an instruction trace fault is
taken. The one exception is a traced \mnemonic{EXCP}, whose trace fault is taken before the trap is entered
(Section~\ref{sec:instruction-trace-fault}). Nothing is lost by the wait. Level-sensitive requests stay asserted, a
Level 5 request stays in its pending bit, and a trace fault is still raised. A fault raised by the call itself, such as
a privilege violation or a failed DMA bus access, is serviced as soon as it occurs.

The worst-case wait for an interrupt is therefore the remainder of the current instruction, plus the dispatch slot of a
pending coprocessor call, plus the time a running coprocessor command takes, plus the dispatch slot of the interrupt
itself. A DMA transfer cannot be interrupted, including by Level 5 (Section~\ref{sec:dma-unit}).
Appendix~\ref{appendix:timing} gives the cycle counts.

\subsection{Level 5 NMI-like Behavior}
\label{sec:level-5-nmi-behavior}

Level 5 hardware exceptions behave similarly to a Non-Maskable Interrupt (NMI). Unlike interrupt levels 1--4, which are
level-sensitive (recognized for as long as the request remains active), Level 5 is edge-triggered: it fires once when
the request becomes active, regardless of how long it is held, and must be withdrawn and raised again to fire again.
This avoids spurious Level Five Hardware Exception Conflict faults from a request that simply stays active. The edge is
latched in every CPU state except reset, including bus wait states, a halt (Section~\ref{sec:halt-request}), and
\mnemonic{WAIT}, so a request that is active for at least one clock cycle is never lost. Level 5 cannot be disabled via
the interrupt enable bits in the status register, and will preempt any lower-priority exception handler. However, Level
5 is \textit{not} fully non-maskable. Because faults carry priority 7 (higher than Level 5's priority 6), an L5
interrupt that arrives while a fault is being handled is \textit{queued} in the pending hardware exceptions register
rather than serviced immediately.

Once the fault handler returns via \mnemonic{RETE} and the exception level drops back below 6, the pending L5 interrupt
fires normally.

The pending hardware exceptions register holds a single bit for L5, so only one L5 request can be queued. If a further
L5 request arrives while the L5 pending bit is already set (for example, during a long fault handler), the request is
lost, and the exception unit records the loss in an internal \emph{L5 overrun} flag. This flag is not part of the
status register or any other software-visible register. When the exception unit next selects L5 for dispatch and the L5
overrun flag is set, it clears the flag and raises a Level Five Hardware Exception Conflict fault
(Section~\ref{sec:level-five-conflict-fault}) instead of dispatching L5. The L5 pending bit remains set. Because that
fault is not retryable, \mnemonic{RETE} from its handler resumes the code that was running, and the still-pending L5
interrupt is then dispatched normally. Any number of lost L5 requests while one is queued are reported by a single
conflict fault. The L5 pending bit and the L5 overrun flag are both cleared by reset.

The L5 pending bit is cleared at the moment L5 is selected for dispatch, and set again only if its vector fetch fails.
An edge that arrives after selection, even during the dispatch slot, is therefore a new request: it sets the pending
bit again, and once the L5 handler is running it raises a Level Five Hardware Exception Conflict fault.

This means Level 5 response latency is not deterministic when a fault is in progress. For timing-critical use of the
NMI line, fault handlers should be kept as short as possible.

If a second L5 interrupt arrives \textit{while the CPU is already executing an L5 handler} (exception level 6), it is
not queued. It will raise a Level Five Hardware Exception Conflict fault instead, which consumes the pending request.
See Section~\ref{sec:level-five-conflict-fault}.

These two rules compose in a non-obvious way when a fault is raised \textit{inside} an L5 handler while a second L5
interrupt is pending. Table~\ref{tab:l5-fault-timeline} walks through the sequence step by step.

\section{User Exceptions (Traps)}
\label{sec:user-exceptions}

A user exception occurs when the program executes an \mnemonic{EXCP} instruction that signals the exception coprocessor
that it should trigger an exception. They are usually used by programs running in protected mode to switch to
supervisor mode in a controlled way. They are also referred to as ``traps''. The vectors for user exceptions are in the
\texttt{0x60}--\texttt{0xFF} range. Supervisor code may also name a vector below \texttt{0x60}; the trap still enters
at priority 1 through link register 0, so the handler it reaches does not find its own link register filled in (see
\mnemonic{EXCP} in Chapter~\ref{ch:coprocessor}).

As with hardware exceptions, the return address stored in the link register is the instruction following the
\mnemonic{EXCP} call, so \mnemonic{RETE} resumes the calling program immediately after the trap.

Software exceptions are only accepted from normal execution. If an \mnemonic{EXCP} instruction is executed while any
exception or fault handler is already active, the software exception is ignored, is not queued, and does not fetch its
vector.

\section{Exception Registers}

The SIRC-1 exception coprocessor maintains several special-purpose registers for exception handling.

\subsection{Link Registers}

The exception unit uses banked link registers to store the processor state when an exception occurs. There are eight
link registers in total, indexed 0--7:

\begin{itemize}
	\item Register 0: Software exceptions (traps)
	\item Registers 1--5: Hardware exceptions (interrupts), one for each priority level
	\item Register 6: Faults
	\item Register 7: Fault metadata (stores bus address and bus access type information, see
	      Section~\ref{sec:fault-metadata-register-format} for the format)
\end{itemize}

For registers 0--6 the link register index is the exception's priority minus one, so each priority level has its own
link register. This is what lets a higher-priority exception interrupt a lower-priority handler without software saving
the return address first: the new exception saves its state in its own link register and leaves the interrupted
handler's untouched.

Link registers 0--6 each store three pieces of information; register 7 uses the same layout to hold fault metadata
(Section~\ref{sec:fault-metadata-register-format}):

\begin{itemize}
	\item \textbf{Return Address:} The 32-bit program-counter value to resume at: the address of the faulting instruction
	      for a retryable fault, or the address of the next instruction otherwise (see below), with bits 31--24 carried
	      unchanged from \reg{p}.
	\item \textbf{Return Status Register:} The 16-bit status register value at the time of the exception
	\item \textbf{Saved Exception Level:} The exception level that was active when the exception was taken;
	      \mnemonic{RETE} restores it into \texttt{current\_exception\_level}
\end{itemize}

When an exception occurs, the appropriate link register (determined by the exception priority level) is populated with

and software exceptions) and Instruction Trace Fault, the return address is the address after the current instruction;

\subsection{Fault Metadata Register Format}
\label{sec:fault-metadata-register-format}

The fault metadata register (register 7) stores additional information about faults beyond just the return address. The
Return Status Register field is used to encode fault-specific metadata in the following format:

\begin{figure}[H]
	\centering
	\begin{bytefield}[bitwidth=1.5em]{16}
		\bitheader{0,2,3,4,7,8,11,12,15} \\
		\bitbox{4}{Escalating} & \bitbox{4}{Original} & \bitbox{4}{Fault} & \bitbox{1}{D} &
		\bitbox{3}{BAT}
	\end{bytefield}
	\caption{Fault Metadata Register Status Field Layout}
	\label{fig:fault-metadata-register-layout}
\end{figure}

\begin{itemize}
	\item \textbf{Bits 0--2:} Bus access type (BAT) captured when the fault was raised (3 bits)
	      \begin{itemize}
		      \item \texttt{0x0}: None
		      \item \texttt{0x1}: Instruction fetch
		      \item \texttt{0x2}: Data read
		      \item \texttt{0x3}: Data write
		      \item \texttt{0x4}: Exception vector fetch
		      \item \texttt{0x5}: DMA read burst
		      \item \texttt{0x6}: DMA write burst
		      \item \texttt{0x7}: Reserved
	      \end{itemize}
	\item \textbf{Bit 3:} Double fault flag (1 bit) -- set to 1 if this is a double fault
	\item \textbf{Bits 4--7:} Fault type (4 bits) -- the fault being dispatched; always \texttt{0x08} when the double fault
	      flag is set
	\item \textbf{Bits 8--11:} Original fault type (4 bits) -- for a double fault, the fault that was already being
	      handled, or whose vector could not be fetched (Section~\ref{sec:double-fault}). If a double-fault handler itself
	      faults, this is \texttt{0x08}. Reserved and read as zero when the double fault flag is clear
	\item \textbf{Bits 12--15:} Escalating fault type (4 bits) -- for a double fault, the fault that caused the escalation.
	      Reserved and read as zero when the double fault flag is clear
\end{itemize}

For a double fault, the bus access type and the Return Address field describe the escalating fault. The original
fault's bus access type and address are lost.

Fault types use the following values:

\begin{itemize}
	\item \textbf{\texttt{0x01}:} Bus fault
	\item \textbf{\texttt{0x02}:} Alignment fault
	\item \textbf{\texttt{0x03}:} Segment overflow fault
	\item \textbf{\texttt{0x04}:} Invalid opcode fault
	\item \textbf{\texttt{0x05}:} Privilege violation fault
	\item \textbf{\texttt{0x06}:} Instruction trace fault
	\item \textbf{\texttt{0x07}:} Level five hardware exception conflict
	\item \textbf{\texttt{0x08}:} Double fault
	\item \textbf{\texttt{0x09}:} Bus protection fault
\end{itemize}

The Return Address field of register 7 stores the bus address that was being accessed when the fault occurred. For a
fault that does not access the bus, this field is architecturally undefined. The exception is an invalid-opcode fault
raised during coprocessor dispatch, before any bus access: the low word of the field stores the 16-bit coprocessor
command that could not be dispatched, and the high word is zero. An alignment fault also defines this field: it stores
the odd instruction address. This lets an invalid-opcode handler emulate missing optional coprocessor operations.

Exception handlers can use the \mnemonic{ETFR} instruction to read the fault metadata register and decode this
information to determine how to handle the fault appropriately.

\subsection{Exception Entry}
\label{sec:exception-entry-side-effects}

\paragraph{Acceptance.} Acceptance is decided before the exception-vector fetch, so an exception that is not accepted has no side effects.

\begin{itemize}
	\item A hardware interrupt is accepted only if its line is enabled in the status register and its priority is higher than the
	      current exception level. Otherwise it does not fetch its vector. A disabled interrupt is ignored and not queued; one
	      that is only outranked remains pending, according to the rules in Section~\ref{sec:pending-hardware-interrupts}.
	\item A Level 5 hardware exception that collides with another one raises a Level Five Hardware Exception Conflict fault
	      instead (Section~\ref{sec:level-five-conflict-fault}).
	\item A software exception is accepted only when no exception handler is active.
\end{itemize}

\paragraph{Selection and commit.} A hardware interrupt, software exception or instruction trace fault is selected only when the CSR is empty and no
coprocessor is active (Section~\ref{sec:interrupt-latency}). A fault raised by a coprocessor call or by the command it
started is not held back: it ends the command, clears the CSR, and is dispatched at the next phase 0. The exception
unit then fetches the high word and then the low word of the handler address from the vector table. The state updates
shown in the figure commit as one architectural action, and only after the vector fetch has succeeded. The condition
flags, reserved lower status bits, interrupt-enable bits, and \texttt{SR.A} are preserved in the live status register.

The status register saved in the link register is the value from before entry, with \texttt{SR.P}, \texttt{SR.T}, and
\texttt{SR.EA} unmodified. \mnemonic{RETE} restores it, so a handler can inspect or edit the saved value with
\mnemonic{ETFR} and \mnemonic{ETTR} before returning. \texttt{SR.T} is cleared on entry to every handler, including
fault handlers, so software tracing does not continue into a handler; if it was set before the exception, tracing
resumes after \mnemonic{RETE}. A handler that sets \texttt{SR.T} itself, or runs while \texttt{TRCE} is active, is
traced, except that no trace fault is raised at exception level 7 (Section~\ref{sec:instruction-trace-fault}).

\paragraph{Vector fetch failure.} If a bus or protection fault occurs during an exception-vector fetch, the original exception does not enter and the
remaining phases of its dispatch slot run as no-ops (Section~\ref{sec:exception-and-fault-timing}). The CPU raises the
corresponding fault with the bus access type set to exception vector fetch. If a fault-vector fetch itself fails, the
CPU escalates to a double fault, which keeps the original fault's saved state so it can be recovered
(Section~\ref{sec:double-fault-vector-fetch}). If the double-fault vector fetch fails, the CPU resets.

When the failed fetch belongs to a hardware interrupt, a Level 5 request or a software exception, that exception is not
lost. Link register 6 stores the state the exception would have saved: its return address, and the status register and
exception level from before entry. The fault-metadata register records the vector address with bus access type
\texttt{0x4}. The pending bit of an interrupt, including the Level 5 bit, is set again, so the interrupt is selected
again once the fault handler returns with \mnemonic{RETE}. A software exception is retryable: its return address is the
address of the \mnemonic{EXCP} itself, so \mnemonic{RETE} executes the \mnemonic{EXCP} again.

Every exception-vector fetch is made as a supervisor access. \texttt{PROT} is deasserted for it, even for an exception
taken from protected mode, although \texttt{SR.P} is not cleared until entry commits. A memory controller that blocks
protected-mode access to the vector table therefore does not block exception entry.

\section{Return from Exception}
\label{sec:return-from-exception}

To return from an exception handler, the \mnemonic{RETE} (Return from Exception) instruction restores the saved state
from the current link register:

\begin{enumerate}
	\item The return address is loaded from the link register into the program counter
	\item The saved status register value is restored (including interrupt enable bits)
	\item The saved exception level is restored to \texttt{current\_exception\_level}
	\item \texttt{SR.EA} is set if the restored exception level is non-zero and cleared if it is 0, whatever the saved status
	      register holds, so \texttt{SR.EA} always agrees with the exception level
	\item Execution resumes at the return address
\end{enumerate}

Because \mnemonic{RETE} replaces the whole status register with the saved copy, any change a handler makes to \reg{sr}
-- including the interrupt enable bits -- is undone when it returns. To change the status register that the interrupted
code resumes with, for example to leave an interrupt line disabled, a handler edits the saved copy with \mnemonic{ETFR}
and \mnemonic{ETTR} before \mnemonic{RETE}.

After \mnemonic{RETE}, any pending interrupts that are now eligible to run (higher priority than the restored exception
level and enabled) will be serviced before the next instruction executes.

Executing \mnemonic{RETE} while the current exception level is 0 is architecturally undefined.

Where \mnemonic{RETE} returns depends on the kind of exception:

\begin{itemize}
	\item For the retryable faults (Section~\ref{sec:fault-categories}), it returns to the faulting instruction, allowing it to
	      be retried. This retry is not always a clean undo for a DMA burst (\mnemonic{DMAR}, \mnemonic{DMAW}, \mnemonic{DMAT}),
	      since it performs several bus accesses per instruction; see Section~\ref{sec:dma-fault-retry}.
	\item For the Instruction Trace Fault and for regular exceptions (hardware and software), it returns to the instruction
	      following the one that was executing when the exception occurred.
	\item For the exception dispatch faults (Level Five Hardware Exception Conflict and Double Fault), it returns to the program
	      counter at the point the fault was detected. A double fault caused by a failed fault-vector fetch instead returns to
	      the original fault's return address (Section~\ref{sec:double-fault-vector-fetch}).
\end{itemize}

\subsection{Accessing Link Registers}

The exception coprocessor provides instructions to transfer data to and from the link registers:

\begin{itemize}
	\item \textbf{\mnemonic{ETFR} (Exception Transfer From Register):} Copies the return address and/or status register from a link register to the address register and/or \reg{r7}
	\item \textbf{\mnemonic{ETTR} (Exception Transfer To Register):} Copies the address register and/or \reg{r7} to a link register's return address and/or status register
\end{itemize}

These instructions allow exception handlers to examine or modify the saved processor state before returning, enabling
features like system calls, context switching, and debuggers.

\section{Halt Request}
\label{sec:halt-request}

The halt request (\texttt{HALT}) lets external hardware stop the CPU, for example so that a debugger can examine the
system. It is sampled at every instruction boundary. If it is active there, the CPU stops before the next instruction
fetch; an instruction in progress, including its coprocessor dispatch slot, always completes first. While halted it
issues no bus cycles and executes nothing. When the request is withdrawn, the CPU resumes at the next instruction
boundary as if it had never stopped. The halt is the state of this request and nothing else: no instruction enters or
leaves it, and it is not saved by exception entry.

While halted, interrupt lines are still sampled under the normal rules, and a Level 5 edge is latched
(Section~\ref{sec:level-5-nmi-behavior}). Nothing is dispatched until the CPU resumes: requests latched during the halt
are taken at the first instruction boundary after the halt request is withdrawn. A reset ends a halt at once. The
\textit{SIRC-1 Hardware Reference Manual} describes the pin that carries the request.

\section{Reset and Startup}

Reset can be initiated externally by raising the reset request (\texttt{RSTI}), or in software by executing the
privileged \mnemonic{RSET} meta-instruction. Both paths converge on the same reset-vector sequence: the CPU holds reset
output active, then the exception unit fetches vector \texttt{0x00} and loads the fetched target address into the
program counter.

Because the status register is cleared to \texttt{0x0000} as part of the reset sequence, hardware interrupt lines 1--4

hold or the reset-vector fetch. The status register, the exception level and the pending hardware exceptions are all
cleared at the moment reset is requested, so nothing latched before the reset survives it and the old enable bits never
admit a request during the hold.

\subsection{Reset Output Hold}
\label{sec:reset-output-hold}

While reset is active, the CPU asserts the reset output (\texttt{RSTO}) and performs no bus cycles. This gives external
devices that share the reset signal time to complete their own reset sequence before the CPU resumes.

For hardware reset, raising \texttt{RSTI} immediately aborts any current instruction, exception handler, exception
dispatch, or pending bus wait, then asserts \texttt{RSTO}. If \texttt{RSTI} remains active, \texttt{RSTO} remains
asserted and the CPU does not advance. After \texttt{RSTI} is withdrawn, the reset hold completes before the CPU
resumes. The reset assertion cycle counts as the first reset-output cycle; after release, five additional countdown
cycles occur before the exception unit starts the reset-vector fetch.

For software reset, \mnemonic{RSET} completes as a normal coprocessor meta-instruction. When its write-back phase
commits the reset command, the CPU requests reset and \texttt{RSTO} is asserted for six cycles before the reset-vector
fetch begins.

\subsection{Reset Vector Fetch}
\label{sec:reset-vector-fetch}

The reset vector is vector \texttt{0x00} in the exception vector table. After the reset-output hold, the exception unit
performs an exception-vector fetch with bus access type exception vector fetch:

\begin{enumerate}
	\item Read the high word of the reset target address from \addr{0x0000}.
	\item Read the low word of the reset target address from \addr{0x0001}.
	\item Load the fetched target address into \reg{p}.
\end{enumerate}

Like every other exception-unit dispatch, the reset-vector fetch occupies one six-phase slot; step 3 happens in its
execute phase. See Appendix~\ref{appendix:timing} for the cycle counts, including the reset-output hold described in
Section~\ref{sec:reset-output-hold}.

If a bus or protection fault occurs during the reset-vector fetch, the reset target is not loaded and no fault is
raised: there is no valid state to save and no handler can be assumed to be reachable. The CPU re-enters reset instead,
asserting \texttt{RSTO} for a further six-cycle hold before it tries the reset-vector fetch again, and keeps doing so
until the fetch succeeds.

\subsection{Internal Instructions}

The following opcodes are used internally by the exception unit and are not directly accessible via user instructions:

\begin{itemize}
	\item \textbf{Fault (\texttt{0xE}):} Automatically invoked when a fault condition is detected
	\item \textbf{HardwareException (\texttt{0xF}):} Automatically invoked when a hardware interrupt is signaled
	\item \textbf{None (\texttt{0x0}):} No operation, used when no exception is pending
\end{itemize}

These internal operations follow the standard exception handling flow described in
Section~\ref{sec:exception-processing}. Issuing opcode \texttt{0xE} or \texttt{0xF} directly, for example via a
supervisor-mode \mnemonic{COPI} instruction, is architecturally undefined.

\subsection{Coprocessor Select Register (CSR)}
\label{sec:coprocessor-select-register}

The coprocessor select register (CSR) is a 16-bit internal register used to select the target coprocessor and
coordinate exception handling. Section~\ref{sec:coprocessors-and-csr} describes how it is used when dispatching. It has
the following structure:

\begin{itemize}
	\item \textbf{Bits 15--12 (First Nibble):} Coprocessor ID (\texttt{0x1} for exception unit, \texttt{0x0} for processing
	      unit)
	\item \textbf{Bits 11--8 (Second Nibble):} Coprocessor opcode (the operation to execute)
	\item \textbf{Bits 7--0 (Third and Fourth Nibbles):} Vector or parameter value
\end{itemize}

The exception unit loads the CSR when a pending exception needs to be serviced. For a hardware interrupt, software
exception or trace fault it waits until the CSR is empty and no coprocessor is active, so such an exception never
replaces a command written by \mnemonic{COPI} or \mnemonic{COPR} (Section~\ref{sec:interrupt-latency}). A fault raised
by the call or its command replaces the command, which ends. For the commands the exception unit builds itself to
dispatch a fault or a hardware exception, the priority is determined by the high nibble of the vector ID, calculated as
7 minus the value of that nibble (for example, \texttt{0x00} is priority 7 and \texttt{0x40} is priority 3). A software
exception (\mnemonic{EXCP}) is always priority 1, whatever its vector.

A CSR value of \texttt{0x0000} -- the value left in place once the reset sequence has completed, and whenever no
exception is pending -- selects coprocessor ID \texttt{0x0}, the processing unit, so the CPU simply continues executing
the program normally in the absence of any exception activity.
