\chapter{Undocumented Instructions}
\label{appendix:undocumented}

\section{Overview}

The SIRCIS instruction set includes two undocumented instruction opcodes, \opcode{27} and \opcode{2F}. They have no
public assembly syntax and are reserved for expansion in future CPU revisions. Their behavior is architecturally
undefined: an implementation decodes them without raising an invalid-opcode fault, but what they do is not part of the
architectural contract and may change in any later revision. Software must not use them.

Undefined and undocumented encodings remain bound by the privilege rules. In protected mode they cannot change the
privileged byte of the status register, a high word of an address register, or the state of the exception unit, and
they may write only the registers named in their fields.

\textbf{Warning:} Undocumented instructions must not be used in production code.

\section{Undefined Operand Combinations}

Undefined operand combinations differ from undocumented opcodes: the opcode is documented, but a particular choice of
operands writes the same address-register pair more than once during one instruction. The privilege rules in the
Overview apply to these combinations.

\subsection{Aliased Address-Register Writes}

The auto-update effective-address forms can write both a destination address-register pair and an updated source
address-register pair. \mnemonic{LDEL} also writes the link-register pair. Any of the following is architecturally
undefined:

\begin{itemize}
	\item two write-back targets in the same address-register pair, including the link write and the program-counter advance
	\item a \mnemonic{LOAD} post-increment whose destination is a half of the updated pair
	\item a \mnemonic{STOR} pre-decrement whose source is a half of the updated pair
\end{itemize}

\begin{lstlisting}
; Undefined: a is both destination and auto-updated source
LDEA a, -(#0, a)

; Undefined: l is both link register and auto-updated source
LDEL p, (#0, l)+

; Undefined: l is both link register and destination
LDEL l, (#0, a)

; Undefined: the auto-update of p competes with the program-counter advance
LOAD r1, (#0, p)+
\end{lstlisting}

Programs must not use aliased register writes. The assembler rejects the known hazardous forms so that programs do not
accidentally depend on undefined write-back ordering.

\section{Implementation Notes}

\subsection{Implementation Behavior}

An implementation -- whether an emulator or a hardware implementation -- decodes undocumented instructions normally
rather than rejecting them. Their exact behavior depends on implementation details and is not part of the architectural
contract. It is not required to be preserved in future CPU revisions.

\section{Why Undocumented?}

These instructions were left undocumented for two reasons:

\begin{enumerate}
	\item \textbf{Opcode space reservation}: the opcodes may be used for future features.
	\item \textbf{Implementation flexibility}: the opcodes allow hardware optimizations.
\end{enumerate}

\section{Recommendations}

\subsection{For Application Developers}

\textbf{Applications must not use undocumented instructions in production code.}

\begin{itemize}
	\item Behavior may change between CPU revisions.
	\item Assemblers may reject them or emit warnings.
	\item Code may not be portable.
	\item Debugging tools may not recognize them.
\end{itemize}

\subsection{For Compiler Writers}

\begin{itemize}
	\item Compilers must not generate undocumented instructions.
	\item Use only documented instructions for all operations.
	\item If optimization requires new operations, request formal documentation.
\end{itemize}

\subsection{For Hardware Implementers}

\begin{itemize}
	\item Document any implementation-specific behavior.
	\item Consider reserving them for future standardization.
\end{itemize}

\section{Future Standardization}

Either undocumented opcode may be formally specified in a future SIRCIS revision, or repurposed. Until then, software
must not depend on either.

\section{Opcode Space for Expansion}

The SIRCIS instruction set has limited expansion space:

\begin{itemize}
	\item Two undocumented opcodes, \opcode{27} and \opcode{2F}, reserved for future revisions
	\item The reserved shift type (111) could enable additional shift modes.
	\item The reserved status-update source encoding (AF = 11) could select a new flag-update source. Until then, an ALU
	      instruction with AF = 11 completes and writes its result, but N, Z, C, and V are architecturally undefined (see
	      Chapter~\ref{ch:instruction-formats}), and assemblers never emit it.
	\item Standard optional coprocessors and model-specific coprocessors can provide extended functionality through the
	      documented coprocessor compatibility rules.
\end{itemize}

Any future expansion must maintain backward compatibility with existing code.
