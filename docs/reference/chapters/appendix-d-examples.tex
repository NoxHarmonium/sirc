\chapter{Example Programs}
\label{appendix:example-programs}

This appendix contains sample programs that demonstrate several features of the CPU.

\section{Program Conventions}

The assembly syntax used in these programs is summarized in the Assembly Language Summary in the Notation and Glossary
chapter, and described in full in the \asmmanual{}.

Every program in this appendix that is loaded at segment zero begins with a \texttt{.ORG 0x0000} / \texttt{.DQ @label}
pair, which places the reset vector (Chapter~\ref{ch:exceptions}): the CPU begins execution by reading a stored pointer
from word addresses \texttt{0x000000}--\texttt{0x000001}, not by executing whatever instruction happens to be placed
there. The separately mapped high segment and the standalone data segment shown later do not need one.

Examples stop the simulator by storing \imm{1} to the DEBUG device's exit register at word address \texttt{0x0B0007}.
This simulator-only interface uses ordinary \mnemonic{MOVI}/\mnemonic{STOR} instructions; it is not an architectural
CPU halt operation. The exit sequence preserves result registers \reg{r1}--\reg{r7} but uses address-register scratch
space. A termination request is not a success result: each example's checks inspect its output. The full interface and
protected-mode usage are described in the Using the Toolchain chapter of the \asmmanual{}.

\section{Byte Sieve}

This program computes primes below 1000 using the Sieve of Eratosthenes, storing one word per candidate number in a
memory-mapped array rather than in a register or the stack. It is a compact illustration of addressing-register setup
(\reg{ah}/\reg{al} and \reg{sh}/\reg{sl}) and of using \mnemonic{STOR} and \mnemonic{LOAD} with an indexed effective
address to walk an array. The two nested loops starting at labels \texttt{:2} and \texttt{:3} (lines 35--50) are the
core of the sieve: the outer loop advances the candidate, and the inner loop marks its multiples as composite.

\section{Faults}

This pair of programs exercises every fault type the CPU can raise and the vector table that routes them to handlers.
\texttt{faults.sasm} deliberately triggers, in sequence, a bus fault, an alignment fault, two segment-overflow faults
(one from an effective-address calculation, one from program-counter overflow), an instruction-trace fault, a
bus-protection fault, a privilege violation, a level-five interrupt whose handler raises a second level-five request
and so a level-five conflict fault, and finally an invalid-opcode fault (which itself triggers a nested double fault).
Each handler, defined from line 158 onward, adds a handler-specific amount to one of \reg{r1}--\reg{r6}, so the final
register dump shows which faults fired. The segment-overflow handler (lines 197--242) is worth particular attention: it
reads exception metadata with \mnemonic{ETFR} to distinguish a program-counter overflow, which records no bus access,
from a \mnemonic{LOAD} or \mnemonic{STOR} effective-address overflow, which records a data read or write, before
deciding how to fix up the return address.

\section{Hardware Exception}

This example shows a device-driven interrupt handled through the serial device: the program prints a help message,
waits on \mnemonic{WAIT} for a hardware exception, and exits once the handler reports that the expected character has
arrived in \reg{r7}. The exception handler itself is installed at vector \texttt{0x40} (word address \addr{0x0080}) and
defined from line 137 onward; it saves the link register, calls \texttt{read\_pending\_byte} and
\texttt{write\_pending\_byte} in turn, and restores the link register before returning with \mnemonic{RETE}. Those two
subroutines show the poll-and-acknowledge pattern used to drain and refill the serial device's receive and send buffers
one byte at a time.

\section{Software Exception}

This short program demonstrates a software-raised exception with \mnemonic{EXCP} and confirms that nesting is blocked
while a handler is running. It sets \reg{r1} to 1, raises exception \addr{0x60}, and expects \reg{r1} to hold
\texttt{0xFF} once the handler at line 26 has run. That handler itself raises a second exception, \addr{0x61}, from
inside the handler; because the handler at address \addr{0x0500} (line 37) sets \reg{r1} to \texttt{0xBB} only if it
runs, the final value of \reg{r1} shows whether the nested exception was correctly ignored.

\section{Store Load}

This program is a self-checking test of indexed and immediate-offset memory access, followed by an exercise of the
register-offset and immediate-offset forms of \mnemonic{LJMP} and \mnemonic{LJSR}. The store and load block (lines
8--19) round-trips values through memory using an immediate offset and a register offset from an address-register pair.
The remainder of the listing chains together register-offset, immediate-offset, and plain register forms of
\mnemonic{LJMP} and \mnemonic{LJSR}; every path not on the intended route lands on an \texttt{LJMP s}/\texttt{LJSR s}
instruction commented \texttt{FAIL!}, so a working implementation reaches the \texttt{:pass} label at the end while a
faulty one jumps into the "forbidden zone" and fails at \texttt{:fail}.
